# RVV Coverage Matrix for ARM NEON/SVE Optimized Paths

Audit date: 2026-06-17

This document tracks how much of the LiteRT CPU code that has ARM NEON,
ARM64-specific, or `GEMMLOWP_NEON` optimized paths currently has an equivalent
RISC-V RVV path.

The audit is intentionally conservative for the RVSPOC S2602 requirement:

- `Done` means a direct RVV path is present, it is used by the optimized kernel
  path, and targeted correctness coverage exists in `rvv_ops_test.cc` or in a
  model-level RVV test.
- `Partial` means RVV exists but coverage is limited by dtype, shape, dispatch,
  single-rounding mode, scalar-per-lane math, or benchmark maturity.
- `Missing` means an ARM optimized path was found but no equivalent RVV path was
  found in the inspected source.
- `Need audit` means the ARM path is indirect, legacy, generated by a library,
  or otherwise not yet mapped to a concrete RVV ownership decision.
- `Not counted` means no clear ARM NEON/SVE optimized path was found in the
  inspected LiteRT CPU kernel tree; RVV code may still exist, but it should not
  be counted toward the NEON/SVE 90% requirement without further evidence.

No SVE-specific LiteRT CPU kernel paths were found in the inspected tree. The
current ARM coverage source is primarily NEON, ARM64-specific code, and
`GEMMLOWP_NEON`.

## Current Coverage Risk Summary

The project has broad RVV functional coverage for common elementwise,
activation, quantization, pooling, reduction, depthwise, convolution,
fully-connected, recurrent, and tensor-manipulation code. It should not yet be
claimed as satisfying the S2602 "90% of existing ARM Neon/SVE optimized kernels"
requirement, because many rows above are only partially covered or still missing.

Highest-risk gaps:

1. `tensor_utils.cc` still routes `USE_RVV` to portable tensor utils. The
   existing `rvv_tensor_utils.h` is a copy/fill helper, not a replacement for
   the `neon_tensor_utils.h` matrix/vector API surface.
2. `optimized/4bit/neon_*` has no RVV equivalent.
3. Sparse and shuffled fully-connected paths have no clear RVV replacements.
4. Several quantized RVV paths are compiled only when `!TFLITE_SINGLE_ROUNDING`;
   these should be treated as partial coverage until the target build policy is
   fixed and documented.
5. Depthwise general and per-channel coverage is useful but not complete across
   depth multipliers, activation ranges, padding/stride cases, and transitional
   paths.
6. Some rows have correctness tests but no real hardware performance evidence;
   S2602 scoring also needs A210 benchmark logs.

## Next Audit Steps

1. Turn the table into a function-level checklist keyed by exact source symbol,
   especially for `neon_tensor_utils.h` and `legacy_optimized_ops.h`.
2. Decide and document the target quantized rounding mode. If
   `TFLITE_SINGLE_ROUNDING=1` is part of the target build, implement RVV for the
   affected paths instead of relying on scalar fallback.
3. Add one-to-one RVV tensor utility functions or explicitly document which
   NEON tensor utility entry points are unreachable in the target model set.
4. Add shape-driven tests for MobileNetV1, MobileNetV2, and EfficientDet-Lite0
   operator patterns, not only synthetic vector-boundary tests.
5. Run correctness under QEMU or hardware with VLEN 128, 256, and 512, then add
   A210 benchmark evidence for the model-level rows.
